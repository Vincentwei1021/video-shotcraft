# storyboard-doc — 出片随附分镜脚本文档（`out/<work名>-storyboard.md`）

每次成片终渲通过后、交付前，在 `out/` 固定输出一份 Markdown 分镜脚本文档，
文件名 `<work名>-storyboard.md`，与成片 `<work名>.mp4` 同名配对。**飞书沉淀是
默认交付环节**：Markdown 落盘后，在工作区约定的飞书 wiki 父节点（约定位置见
工作区 CLAUDE.md 的「飞书沉淀」条目）下新建一个 docx 子文档，把同一份语义结构
按原生块写入并回读验收；不要另写一套内容不同的飞书版本。工作区未约定父节点时
询问用户一次，用户明确不要飞书版本则只交付 Markdown。

本规范来自历次用户裁决与已验收的产品宣传片分镜文档结构。只沉淀可复用的信息
层级和真实性规则，不固化任何单个项目的时长、功能、镜头数、品牌色或技术栈。

## 固定信息层级

顺序固定；具体条目数按项目事实变化。

1. **文档标题**：`<产品名> 宣传片｜Storyboard`（全角竖线；飞书子文档节点
   标题与文档标题一致）。
2. **开篇摘要**：用一段话交代实际时长、分辨率、帧率、语言、交付版本和一句话
   核心叙事。卡点片再补 BGM 的实测节奏，以及镜头边界/关键动效如何对拍；没有
   验证过 BPM 或卡点误差时不要写。
3. **引导块 ×2**（Markdown 用 blockquote，飞书用原生 callout）：
   - 🎬 **脚本主线与功能覆盖**：按叙事顺序点名产品功能，并交代呈现形式、
     结构骨架、受众和语言。信息来自阶段 0 产品简报，此处负责面向读者落位。
   - 📌 **素材怎么来 / 素材原则**：用人话说明真实截图（整页/单元素）、真实产物、
     官方素材和代码绘制的边界；代码绘制必须解释为何静态素材无法承担该动作，
     且不能冒充真实产品页面。
4. **逐镜说明**：先设一个总章，再逐镜展开。Markdown 使用 `## 逐镜说明` +
   `### 镜号 · 镜名（起–止时间）`；飞书使用 H1 总章 + H2 镜头标题。
5. **选材偏向**：先写核心取舍结论，再写可验证的判断依据、舍弃内容与理由，
   最后落回全片统一的真实性纪律。
6. **工程与留档**：工程路径、两版成片路径、分镜文档路径，以及设计规范、节拍
   网格、审核记录等关键决策链所在位置。

## 每镜语义契约

每镜标题后紧跟一张从最终成片抽出的代表帧，随后按顺序说明：

- **内容**：这一镜实际发生什么，关键屏幕文案原样写明。
  - **对应功能**：明确映射到产品能力；纯转场、呼吸或品牌镜写“不引入新功能”。
- **素材**：逐项说明真实截图/界面切片、真实生成结果、官方文件或代码绘制，并
  写清真实性边界。
- **动画**：镜头卡或动作语法 + 一句普通读者能理解的运动描述。
- **选择理由**：说明产品证据、叙事职责和节奏位置，而不是泛泛写“更好看”。

强制的是语义齐全，不是机械凑五条视觉标签。呼吸字卡等简单连接镜允许合并为
“内容与理由”，但仍要说明它不承担新功能、为何存在、位于什么节奏位置。

## 飞书子文档创建（默认环节）

终渲交付时按下面顺序执行；基准样例是 YouArt 宣传片的飞书 storyboard
（wiki `Dr8VwDAZXis1Yek2zTklxXrDgrc`），标题结构以其为准：

1. 用 lark-wiki skill 在约定父节点下建 docx 子节点（身份用 `--as user`）：
   `lark-cli wiki +node-create --parent-node-token <约定父节点> --title
   "<产品名> 宣传片｜Storyboard" --as user`；
2. 用返回的 `obj_token`（docx）按下面的原生块映射写入内容；
3. 按「写入后验收」重新读取远端文档核对。

## 飞书原生结构映射

飞书版本必须保持上面的语义层级，不把 Markdown 当纯文本粘贴。使用 `lark-doc`
原生块写入：

```xml
<title>&lt;产品名&gt; 宣传片｜Storyboard</title>
<p>&lt;版本信息 + 一句话核心叙事&gt;</p>
<callout emoji="🎬" background-color="light-blue" border-color="blue">
  <p><b>脚本主线与功能覆盖</b>：……</p>
  <p><b>呈现形式</b>：……</p>
</callout>
<callout emoji="📌" background-color="light-purple" border-color="purple">
  <p><b>素材原则</b></p>
  <ul><li>……</li></ul>
</callout>
<h1>逐镜说明</h1>
<h2>S1 · &lt;镜名&gt;（0:00–0:06）</h2>
<img path="@./out/storyboard/s1.png" caption="S1：&lt;画面落定态&gt;"/>
<ul>
  <li><b>内容</b>：……<ul><li><b>对应功能</b>：……</li></ul></li>
  <li><b>素材</b>：……</li>
  <li><b>动画</b>：……</li>
  <li><b>选择理由</b>：……</li>
</ul>
<h1>选材偏向：&lt;结论式标题&gt;</h1>
<p>&lt;核心取舍结论&gt;</p>
<h2>判断依据</h2>
<ol><li>……</li></ol>
<h2>舍弃的内容与理由</h2>
<ul><li>……</li></ul>
<p>&lt;真实性纪律总结&gt;</p>
<h1>工程与留档</h1>
<p>……</p>
```

- 先读取目标文档。空文档可完整写入；非空文档按现有 block 局部更新，不用
  `overwrite` 抹掉原内容或评论。
- 分镜图只上传 `out/storyboard/` 的本地终渲抽帧，不复用带临时鉴权参数的图片 URL。
- callout 色彩可按目标产品克制调整，但两个引导块的职责和顺序不变。
- 图片 caption 写镜号 + 画面落定态（`S1：<落定态>`），不重复整段正文；图片块
  紧跟镜头 H2、位于该镜列表之前。
- 「选材偏向」正文以「先说结论：**<取舍结论>**」开头；「判断依据」的 H2 允许
  按证据来源写成陈述式标题（如「源码给了三个判断依据」），无特定来源时用默认
  标题「判断依据」。

## 选材偏向的证据要求

- 判断依据只写当前项目确实拥有的证据：产品信息层级、真实账户/数据状态、设计
  系统、源码或官方资料；不强制固定数量，也不强制必须有源码。
- 舍弃清单逐项写“没拍什么 + 为什么”，不能只列已拍内容。
- 结尾用一句可执行的真实性纪律收束，例如“能用真截图就不自己画，能真实跑出来
  就不摆拍”；措辞按项目事实改写。

## 文风规则（违反必返工）

- **陈述句**：标题与标签不用问句（“要展现什么”→“脚本主线与功能覆盖”；
  “为什么”→“选择理由”）。
- **说人话**：内部行话（手搓、切片、backplate、蒙皮等）改成普通表达，或首次
  出现即解释；读者是产品/业务同事，不是本 skill 用户。
- **不用表格**：靠标题、短列表、嵌套列表和引导块建立层级。
- **每镜一张终渲帧图**：存 `out/storyboard/`，选该镜信息最完整的落定态，顺序
  与镜头一致。
- 每个字段一到三句，不堆修饰；项目专属数字、模型名和工程细节必须有证据。

## 写入后验收

不能只相信写入接口的成功返回；重新读取远端文档并核对：

- 标题、开篇摘要和两个引导块存在；
- “逐镜说明”总章存在，镜头标题数等于最终时间线镜头数；
- 图片数等于需要画面帧的镜头数，顺序与镜头一致；
- 每镜的内容、对应功能、素材、动画和选择理由语义齐全；
- 选材偏向含结论、判断依据、舍弃清单和真实性纪律；
- 工程与留档包含当前 work 的真实路径；
- 飞书图片是原生图片块，不是失效的临时外链。

## 与流水线的挂接

- 功能到镜头映射在阶段 0 产品简报里成形，本文档只做读者向表达。
- 阶段 7 终渲通过后生成 Markdown，与成片一起交付；内容与 DESIGN_SPEC 一致，
  但面向产品/业务读者重写，不复制内部 spec。
- 沉淀飞书是默认交付环节：Markdown 落盘后，按「飞书子文档创建」在约定父节点下
  建子文档、按原生映射写入并回读验收；仅当工作区未约定父节点且用户明确不要时
  跳过。
